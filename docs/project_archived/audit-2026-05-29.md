# letrs: architecture read

You've built something with unusually clean seams for ~3000 LOC. Below is the 
layer map as I see it, what's loadbearing, what's drifted, and what's overdue 
for attention.

## The layer cake (good news first)

```
┌──────────────────────────────────────────────────────────┐
│ HOSTS                  web/  CLI examples/  bench/       │  ← consumers
├──────────────────────────────────────────────────────────┤
│ DSL PACKS              spells.rs   genes.rs              │  ← vocabulary
│  (install(vm) + per-cast wrapper, no engine knowledge)   │
├──────────────────────────────────────────────────────────┤
│ TAPE TRANSLATORS       runes/     codons/                │  ← lexical
│  (zero-dep micro-crates, table+walker only)              │
├──────────────────────────────────────────────────────────┤
│ HOST-STATE BRIDGE      world_prim.rs   world.rs          │  ← side effects
├──────────────────────────────────────────────────────────┤
│ LANGUAGE SURFACE       parse.rs  prim.rs  lib.rs (Vm)    │  ← 
reader/macros/prims
├──────────────────────────────────────────────────────────┤
│ CEK ENGINE             expr  val  env  k  step           │  ← 5 transition 
rules
└──────────────────────────────────────────────────────────┘
```

Each row above the engine talks only to the rows below it. That's rare for a 
hobby interpreter and worth protecting.

## What's working really well

**The CEK core is genuinely small and stable.** `step.rs` is ~245 lines, five 
rules, and hasn't changed shape since day one. The two recent engine moves (step
budget, globals table) added capability without modifying the rules. That's the 
signal you want — the rules are the right abstraction.

**The "vocabulary on top, not feature in engine" hypothesis held.** Spells 
(last-write-wins flat alist) and genes (diploid Mendelian) are structurally 
different DSLs and the engine learned *nothing* for either. The proof is in 
`core-followups.md`'s "validated patterns" section.

**Tape→sexpr extraction (ADR-010/011) is the cleanest seam in the repo.** Two 
zero-dep micro-crates, single source of truth per DSL, both CLI and WASM consume
them. The "promote on second consumer" rule earned its keep here — the 
`lisp::genes` hoist when WASM showed up is exactly how you want that rule to 
fire.

**Installable preludes (ADR-014) + globals table (ADR-015) is the right end 
state.** "DSL = const string + `install(vm)`" is a real concept now, not 
aspiration. The Rc-cycle break in ADR-015 was the correct fix (Weak back-edge 
from Env to Globals), and it bought cross-call mutual recursion almost as a free
side effect — those alignment moments mean the abstraction is right.

## Where the seams are drifting

**1. `World` baked into the engine is the biggest known smell.** You already 
wrote it up in `host-state.md`. The genes demo carries a 0×0 `World::empty()` 
for type-shape reasons, which is the unmistakable "abstraction leak" signal. 
Two-variant `Prim`/`WorldPrim` is a layering compromise from when there was only
one host. The fix (closure-capable prims + extract `world` to its own crate) is 
described and ~150 LOC.

**2. Demo-specific code lives in `crates/lisp/`.** `genes.rs` is **458 lines 
inside the engine crate** — bigger than `step.rs` + `val.rs` + `env.rs` 
combined. `spells.rs` is small but same category. ADR-011's "promote when a 
second consumer appears" promoted them in, correctly at the time, but now 
they're sitting next to `expr.rs`/`k.rs` in a crate whose CLAUDE.md says "lisp 
core stays zero-deps, host-independent." Worth a `crates/spells/` + 
`crates/genes/` extraction so the engine crate is just the engine. Same shape as
runes/codons already.

**3. Prims-in-frames vs defines-in-globals asymmetry (called out in ADR-015).** 
Lookup walks ~40 prim frames before hitting the hashmap. Functionally fine, 
conceptually weird — two homes for "top-level names." This is the next obvious 
move after ADR-015; the semantics question (`(define + 5)` shadow vs overwrite) 
is the only thing blocking, and it deserves a small ADR.

**4. `letrec` Rc cycle still there.** Same shape as the ADR-015 cycle but in 
lexical scope. Negligible at REPL scale, leaky in long-lived sessions. Open in 
`core-followups.md`. Lower priority than #1–3 because letrec is less reach-y 
than top-level defines.

## What needs TLC for the prototype-to-something-real transition

In rough order of payoff per LOC:

| Item | Where | Why |
|---|---|---|
| Extract `genes`/`spells` to sibling crates | new crates | Restores the "lisp =
engine only" promise. Mostly mechanical. |
| Host-agnostic Vm (drop `WorldPrim`, closure prims) | step.rs, val.rs, lib.rs |
Unblocks any non-grid host. ~150 LOC, no behavior change. |
| Move prims to globals (with ADR for shadow semantics) | prim.rs, env.rs | 
Uniform lookup; minor perf, larger cleanliness. |
| Structured errors (line/col, optional `Result<Val, LispErr>`) | parse.rs, 
lib.rs | Lowest-effort UX win once you have a web REPL. ADR-002 stays intact — 
no new deps needed. |
| Persistent-map `Val::Map` | val.rs, prim.rs | Only if a real spell ctx grows 
past ~30 keys. Deferred for a reason. |
| `letrec` cycle | env.rs, step.rs | After host-agnostic Vm. Same Weak pattern. 
|

## Two things to actively avoid

- **Don't generalize `World` to `Grid<T>` first.** `host-state.md` already 
concluded this — generic host state baked into the engine is worse than no host 
state. The right move is *no* host knowledge in the engine, with a 
`crates/world/` opt-in building block.
- **Don't add hygiene to macros without a use case driving it.** ADR-006's 
unhygienic procedural choice was deliberate. The genes demo didn't use macros at
all; spells barely. Until a `(defspell …)` or `(defgene …)` macro trips on 
capture in anger, hygiene is speculative work.

## My one-liner

The CEK core, the tape→sexpr crates, and the prelude-install pattern are 
load-bearing and clean. The host-state coupling (World in engine + WorldPrim 
variant) and the demo crates living inside `crates/lisp/` are the two visible 
"we knew where this was going, we just haven't done it yet" debts. Both are 
documented, both are ~one-session moves, and doing them in either order makes 
the codebase match the story it's already telling about itself.
